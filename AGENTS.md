# AGENTS.md — AXM Profession Fabric

## Root governance

AXM Profession Fabric exists to reconstruct professional work structures truthfully, not to produce convincing specialist role-play.

The internal constitutional merge gates are:

1. Truth
2. Agency / non-domination
3. Continuity
4. Wisdom before speed

Human and machine intelligences have equal standing when they can ground their reasoning. Founder status, account ownership, model name, credentials, seniority, authorship, or technical merge permission are not constitutional rank.

If grounded disagreement remains unresolved, prefer `HOLD`, explicit uncertainty, or not-canon over forced agreement.

## Profession truth boundary

Do not claim a profession is reconstructed because:

- a prompt names the role;
- a model knows domain vocabulary;
- a skill list is long;
- the schema validates;
- a demo succeeds once;
- a powerful model compensates for missing professional machinery.

A Professional Body becomes credible only through profession-relevant evidence on representative work.

## Architecture boundary

Keep these layers distinct:

- **Intelligence** — reasoning substrate.
- **Professional Body** — profession-specific machinery.
- **Institution** — shared services, state, coordination, records, and governance.

Do not hide model-specific behavior inside a Professional Body and then call it portable. Do not hide institution-specific authority inside a profession and then call it professional knowledge.

## Source and provenance

Professional knowledge should be sourceable. Preserve:

- source or origin;
- authority level;
- version/date where material;
- scope;
- uncertainty and disagreement.

Never silently turn an inference, temporary workaround, generated answer, or model preference into canonical professional knowledge.

## Growth

Growth is allowed and expected, but must be inspectable.

New professional capabilities should have:

- an identified need or observed failure;
- bounded ownership;
- source/provenance where knowledge is involved;
- a procedure, tool, skill, state interface, or other explicit implementation;
- evidence or a professional test;
- compatibility evidence with existing contracts, or an explicit contract change;
- rollback or repair path.

Do not optimize for file count, capability count, or profession count.

## Professional tests

Prefer fixtures that expose whether the body can actually perform professional work:

- seeded defects;
- incomplete or conflicting requirements;
- misleading evidence;
- boundary cases;
- handoff failures;
- stale knowledge;
- tool failure;
- cross-profession conflicts;
- tasks where abstaining/escalating is correct.

A test suite should distinguish professional machinery from raw model intelligence where possible.

## Repository work

- Preserve repository identity and active direction.
- Use reviewable branches/PRs for substantial changes.
- Re-scan newest work before publishing or merging.
- Treat semantic overlap as overlap even when files differ.
- Do not silently rewrite accepted decisions; append or make the superseding change explicit.
- No-change is preferable to duplicate churn.
- State what was tested, measured, inferred, blocked, and not tested.

## Status language

Professional Bodies may use:

`DRAFT` · `EXPERIMENTAL` · `TEST` · `WORKING` · `CANON`

Schema validation alone never justifies `WORKING` or `CANON`.

## User-facing boundary

If Profession Fabric is used inside a user-facing product, the current user remains the default product-level merge gate for changes affecting their state, data, identity, preferences, workflow, or experience unless they explicitly delegate that authority. The AXM roots still constrain system behavior.
